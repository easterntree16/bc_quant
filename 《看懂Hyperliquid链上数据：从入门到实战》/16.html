数据存储方案：从CSV到PostgreSQL的实战选择

做链上数据分析，最头疼的问题之一就是：数据存哪？

我刚开始做Hyperliquid链上数据抓取时，天真地以为把所有数据都塞进CSV文件就完事了。结果呢？跑了三天，一个CSV文件就膨胀到2GB，打开都费劲。嗯，从那以后我老老实实研究起了存储方案。

今天咱们聊聊四种常见的存储方式：CSV、SQLite、PostgreSQL，以及数据备份策略。每种方案都有它的适用场景，选对了事半功倍。

CSV文件存储：简单粗暴的入门方案

CSV是最直接的存储方式。说白了，就是纯文本表格。每行一条记录，逗号分隔字段。

优点很明显：

  • 人类可读，用Excel就能打开
  • 跨平台兼容，任何语言都能解析
  • 适合小规模数据（几千到几万条）
  • 快速原型开发时特别好用

缺点也很致命：

  • 没有索引，查询慢得像蜗牛
  • 不支持并发写入
  • 数据量大时文件巨大
  • 没有数据类型约束，容易出错

我的建议：CSV只适合做数据导出和临时分析。别把它当主力存储。

举个例子，抓取Hyperliquid的订单簿快照：

import csv
import time

def save_orderbook_snapshot(snapshot, filename="orderbook.csv"):
    with open(filename, 'a', newline='') as f:
        writer = csv.writer(f)
        writer.writerow([
            time.time(),
            snapshot['bids'][0][0],  # 最高买价
            snapshot['asks'][0][0],  # 最低卖价
            len(snapshot['bids']),
            len(snapshot['asks'])
        ])

这段代码我写过无数次。但注意，如果每秒抓一次，一天就是86400行。一个月下来，CSV文件就变得难以处理了。

SQLite数据库存储：轻量级的中场选择

SQLite是个好东西。它是个嵌入式数据库，不需要安装服务器，一个文件就是一个数据库。

我个人习惯在本地做数据分析时用SQLite。为什么？因为它支持SQL查询，有索引，还能处理几百万条数据不卡顿。

SQLite的优势：

  • 零配置，开箱即用
  • 支持标准SQL语法
  • 支持事务和索引
  • 单文件存储，方便迁移
  • 适合单机应用

局限性：

  • 不支持并发写入（多个进程同时写会报错）
  • 不适合高并发场景
  • 没有用户权限管理
  • 数据量超过10GB后性能下降明显

小技巧：用SQLite存储历史K线数据特别合适。我一般按月份建表，比如klines_2024_01、klines_2024_02，查询时只查需要的表，效率很高。

创建表结构的示例：

CREATE TABLE IF NOT EXISTS trades (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol TEXT NOT NULL,
    price REAL NOT NULL,
    volume REAL NOT NULL,
    side TEXT CHECK(side IN ('buy', 'sell')),
    timestamp INTEGER NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_trades_symbol ON trades(symbol);
CREATE INDEX idx_trades_timestamp ON trades(timestamp);

我曾经用SQLite存储了半年的Hyperliquid交易数据，大概500万条记录。查询某个币种最近1000笔交易，耗时不到0.1秒。够用了。

PostgreSQL存储方案：企业级的选择

当数据量突破千万级别，或者需要多人协作时，PostgreSQL就是最佳选择了。

PostgreSQL是个功能强大的关系型数据库。它支持复杂查询、高并发、数据完整性约束，还有丰富的扩展插件。

为什么选PostgreSQL？

  • 支持高并发读写
  • 强大的索引机制（B-tree、Hash、GiST、GIN等）
  • 支持JSON/JSONB数据类型（存储非结构化数据）
  • 支持分区表（按时间分区，查询更快）
  • 支持流复制和备份
  • 有完善的权限管理

我在项目中遇到过一个问题：用SQLite存储链上事件日志，结果多个数据抓取进程同时写入，导致数据库锁死。换成PostgreSQL后，这个问题就解决了。

PostgreSQL的建表示例：

CREATE TABLE hyperliquid_orders (
    id BIGSERIAL PRIMARY KEY,
    order_id VARCHAR(64) NOT NULL,
    symbol VARCHAR(20) NOT NULL,
    side VARCHAR(4) NOT NULL,
    price NUMERIC(20, 8) NOT NULL,
    quantity NUMERIC(20, 8) NOT NULL,
    status VARCHAR(20) DEFAULT 'open',
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- 按时间分区
CREATE TABLE hyperliquid_trades (
    id BIGSERIAL,
    trade_id VARCHAR(64) NOT NULL,
    symbol VARCHAR(20) NOT NULL,
    price NUMERIC(20, 8) NOT NULL,
    volume NUMERIC(20, 8) NOT NULL,
    side VARCHAR(4) NOT NULL,
    trade_time TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (trade_time);

-- 创建分区
CREATE TABLE hyperliquid_trades_2024_01
    PARTITION OF hyperliquid_trades
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE hyperliquid_trades_2024_02
    PARTITION OF hyperliquid_trades
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

注意：PostgreSQL虽然强大，但需要维护。你得定期清理旧数据、重建索引、监控磁盘空间。别以为部署完就万事大吉了。

数据备份策略：别等数据丢了才后悔

数据备份这件事，我吃过亏。有一次服务器硬盘坏了，三天没备份的数据全丢了。从那以后，我严格执行3-2-1备份策略。

3-2-1备份原则：

  • 3：保留3份数据副本
  • 2：使用2种不同的存储介质
  • 1：至少1份异地备份

具体到Hyperliquid数据备份，我推荐这样做：

备份类型 频率 存储位置 说明
全量备份 每天一次 本地磁盘 + 云存储 导出完整数据库
增量备份 每小时一次 本地磁盘 只备份新增数据
日志备份 实时 异地服务器 WAL日志流复制

PostgreSQL的备份脚本示例：

#!/bin/bash
# 全量备份脚本
BACKUP_DIR="/data/backups/hyperliquid"
DATE=$(date +%Y%m%d_%H%M%S)
DB_NAME="hyperliquid_db"

# 创建备份目录
mkdir -p $BACKUP_DIR

# 执行pg_dump
pg_dump -h localhost -U dbadmin \
    --format=custom \
    --compress=9 \
    --file="$BACKUP_DIR/${DB_NAME}_${DATE}.dump" \
    $DB_NAME

# 删除7天前的备份
find $BACKUP_DIR -name "*.dump" -mtime +7 -delete

# 同步到云存储（示例用rsync）
rsync -avz $BACKUP_DIR/ backup@remote:/data/backups/

我的经验：除了数据库备份，还要备份配置文件。比如数据库连接信息、API密钥、抓取脚本等。这些文件虽然小，但丢了重建起来很麻烦。

如何选择？一张图看懂

下面这张图展示了不同存储方案的适用场景和选择逻辑：

你想想看，如果只是自己研究几个币种的数据，CSV或SQLite完全够用。但如果是团队协作，或者要搭建数据服务，PostgreSQL是必须的。

我个人建议的路线是：先用SQLite快速验证想法，等数据量上来了再迁移到PostgreSQL。别一上来就搞大而全的方案，容易把自己累死。

核心要点总结：

  • CSV：临时方案，别当真
  • SQLite：单机利器，够用就好
  • PostgreSQL：企业标配，值得投入
  • 备份：3-2-1原则，保命要紧

数据存储这件事，说白了就是权衡。没有完美的方案，只有适合的方案。选对了，数据分析事半功倍；选错了，光折腾数据就够你受的。

嗯，今天就聊到这。记住一点：不管用哪种方案，先把备份做好。这是过来人的血泪教训。
