30、实战项目二：链上数据监控机器人：机器人架构设计、Telegram通知集成、多链支持、运维与监控

说实话，做链上数据监控这件事，我踩过的坑比你们想象的多得多。

记得2022年我刚入行时，写了个简单的价格监控脚本，跑在本地笔记本上。结果有一次出门吃饭，笔记本合盖了，机器人直接宕机8小时。那8小时里，某个协议被攻击了，我完全没收到警报。嗯，从那以后，我再也不敢用本地跑生产级机器人了。

今天这个实战项目，我会把这几年的经验全盘托出。咱们要做一个真正能上线的链上数据监控机器人，不是那种玩具demo。

一、机器人架构设计：别一上来就写代码

我见过太多人，拿到需求就开始写Python脚本。结果写到一半发现架构撑不住，又推倒重来。我个人习惯是：先画图，再写码。

核心架构原则：

  • 模块化：数据采集、数据处理、通知发送、配置管理，各模块独立
  • 可扩展：新增一条链，只需要加一个数据源模块
  • 容错性：某个节点挂了，不影响整体运行

二、Telegram通知集成：别用轮询，用长轮询

Telegram Bot API 有两种获取消息的方式：轮询和Webhook。我个人强烈推荐用长轮询（Long Polling），尤其是在自建机器人时。

为什么会这样？因为Webhook需要公网IP和HTTPS证书，很多开发者的服务器在内网环境，配置起来很麻烦。长轮询只需要一个出站连接，简单粗暴。

小技巧：用 python-telegram-bot 库的 Updater 类，默认就是长轮询模式。你只需要一个 Bot Token，5行代码就能跑起来。

from telegram.ext import Updater, CommandHandler

def start(update, context):
    update.message.reply_text('监控机器人已启动！')

def main():
    updater = Updater("YOUR_BOT_TOKEN", use_context=True)
    dp = updater.dispatcher
    dp.add_handler(CommandHandler("start", start))
    updater.start_polling()
    updater.idle()

if __name__ == '__main__':
    main()

我曾经犯过一个低级错误：把 Bot Token 硬编码在代码里，然后上传到了公开的 GitHub 仓库。结果不到10分钟，就有人用我的机器人发垃圾消息。嗯，从那以后，所有敏感信息我都用环境变量管理。

警告：永远不要把 Bot Token、RPC URL、私钥等敏感信息写在代码里。使用 .env 文件或环境变量。

三、多链支持：抽象一个数据源接口

多链支持的核心，是抽象出一个统一的数据源接口。不管底层是 Hyperliquid、Ethereum 还是 Arbitrum，对外暴露的方法应该是一样的。

我一般这样设计：

from abc import ABC, abstractmethod

class ChainDataSource(ABC):
    @abstractmethod
    def get_latest_block(self):
        pass

    @abstractmethod
    def get_transaction(self, tx_hash):
        pass

    @abstractmethod
    def get_token_price(self, token_address):
        pass

class HyperliquidDataSource(ChainDataSource):
    def get_latest_block(self):
        # Hyperliquid 特有的实现
        pass

    def get_transaction(self, tx_hash):
        # Hyperliquid 特有的实现
        pass

    def get_token_price(self, token_address):
        # Hyperliquid 特有的实现
        pass

class EthereumDataSource(ChainDataSource):
    def get_latest_block(self):
        # Ethereum 特有的实现
        pass

    # ... 其他方法

这样做的好处是：新增一条链时，只需要写一个新的子类，实现那几个抽象方法就行。主流程代码完全不用改。

四、运维与监控：机器人自己也要被监控

你想想看，一个监控别人的机器人，如果自己挂了没人知道，那还有什么意义？

我个人的做法是：给机器人加一个「心跳检测」功能。每隔5分钟，机器人给自己发一条测试消息。如果连续3次没收到回复，就触发升级告警——通过另一个独立的渠道通知我。

核心运维指标：

  • 数据延迟：当前区块高度与最新区块高度的差值，超过阈值告警
  • 错误率：RPC 调用失败次数 / 总调用次数，超过1%告警
  • 内存使用：超过 80% 触发告警，超过 90% 自动重启
  • 通知成功率：Telegram 消息发送失败次数，超过5次升级告警

我记得有一次，Alchemy 的免费套餐到期了，RPC 调用全部返回 403。我的机器人还在傻傻地跑，但一条数据都拿不到。幸亏有心跳检测，5分钟后我就收到了告警，赶紧换了 RPC 提供商。

日志管理也很重要。我习惯用 loguru 库，比 Python 自带的 logging 好用太多：

from loguru import logger

logger.add("monitor_{time}.log", rotation="500 MB", retention="10 days")

def check_health():
    try:
        latest_block = data_source.get_latest_block()
        logger.info(f"最新区块: {latest_block}")
    except Exception as e:
        logger.error(f"健康检查失败: {e}")
        # 触发告警
        alert_manager.send_alert(f"健康检查失败: {e}")

避坑指南：我曾经把日志文件设成无限增长，结果一个月后磁盘满了，机器人直接崩溃。现在我的日志策略是：每个文件最大500MB，保留最近10天，自动删除旧日志。

最后，关于部署。我个人推荐用 Docker + docker-compose，配合 restart: always 策略。这样即使进程崩溃，Docker 也会自动重启。再加上一个简单的 crontab 定时检查容器状态，基本能做到 99.9% 的可用性。

好了，这个实战项目的核心思路就这些。从架构设计到多链支持，从 Telegram 集成到运维监控，每一步都有我踩过的坑和总结的经验。你们照着这个框架去实现，应该能少走很多弯路。
