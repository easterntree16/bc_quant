WebSocket 实战（二）：实时成交数据流、用户订单状态推送

好，咱们接着聊 WebSocket。上一章我们把连接和心跳搞定了，这一章要动真格的了——实时成交数据流和用户订单状态推送。这两个东西，说白了就是量化交易的「眼睛」和「耳朵」。没有它们，你的策略就是个瞎子。

实时成交数据流：市场的脉搏

实时成交数据，也叫 trade feed。它告诉你每一笔交易在什么时间、什么价格、成交了多少。我刚开始做高频策略时，一直用 REST API 轮询，结果发现延迟高得离谱，策略根本跑不起来。后来换成 WebSocket 订阅成交流，效果立竿见影。

订阅成交流

Hyperliquid 的成交流订阅格式很简单。你发送一个 JSON 消息，指定类型和币种。我个人习惯把订阅消息封装成一个函数，方便复用。

def subscribe_trades(ws, coin):
    msg = {
        "type": "subscribe",
        "channel": "trades",
        "coin": coin
    }
    ws.send(json.dumps(msg))
    print(f"已订阅 {coin} 的成交流")

嗯，这里要注意：coin 参数必须是大写字母，比如 "BTC"、"ETH"。我之前踩过坑，传了小写，结果半天没收到数据，还以为是网络问题。

解析成交数据

成交数据推送的格式大概是这样的：

{
    "channel": "trades",
    "data": [
        {
            "coin": "BTC",
            "side": "B",
            "px": "50000.0",
            "sz": "0.1",
            "time": 1690000000000,
            "hash": "0xabc123..."
        }
    ]
}

字段说明：

字段 含义
coin 币种
side B 表示买方主动吃单，S 表示卖方主动吃单
px 成交价格
sz 成交数量
time 时间戳（毫秒）
hash 交易哈希，可以用来去重

你想想看，如果每秒有几百笔成交，你每笔都处理，CPU 可能扛不住。我建议你做一个缓冲区，批量处理。比如每 100 毫秒处理一次缓冲区里的数据。

小技巧： 用 side 字段可以快速判断买卖压力。如果连续出现大量 B 单，说明买方在主动买入，价格可能要涨。

用户订单状态推送：你的订单管家

用户订单状态推送，就是交易所主动告诉你：你的订单成交了、部分成交了、被取消了。这比你自己去查快得多。我曾经在做一个做市策略时，全靠轮询查订单状态，结果订单成交了我还不知道，错过了后续操作。后来换成 WebSocket 推送，再也没有这种问题了。

订阅用户订单流

订阅用户订单流需要先认证。你需要用你的 API 密钥生成一个签名，然后发送订阅消息。具体流程如下：

  1. 生成一个随机字符串作为 nonce
  2. 用你的私钥对 nonce 签名
  3. 发送订阅消息，包含你的地址和签名
def subscribe_user_events(ws, address, signature, nonce):
    msg = {
        "type": "subscribe",
        "channel": "user",
        "user": address,
        "signature": signature,
        "nonce": nonce
    }
    ws.send(json.dumps(msg))
    print(f"已订阅用户事件流，地址: {address}")
注意： 签名用的私钥一定要保护好，不要硬编码在代码里。我建议用环境变量或者专门的密钥管理服务。

解析订单状态更新

订单状态更新的消息格式如下：

{
    "channel": "user",
    "data": {
        "type": "orderUpdate",
        "order": {
            "oid": 123456,
            "coin": "BTC",
            "side": "B",
            "px": "50000.0",
            "sz": "1.0",
            "filled": "0.5",
            "status": "partial_filled",
            "timestamp": 1690000000000
        }
    }
}

关键字段：

  • oid：订单 ID，用来关联你的本地订单
  • filled：已成交数量
  • status：订单状态，常见的有 open、partial_filled、filled、canceled

我一般会在本地维护一个订单状态字典，收到推送后立即更新。这样我的策略可以实时知道订单的最新状态。

order_status = {}

def handle_order_update(order):
    oid = order["oid"]
    order_status[oid] = {
        "filled": order["filled"],
        "status": order["status"],
        "timestamp": order["timestamp"]
    }
    print(f"订单 {oid} 状态更新: {order['status']}, 已成交: {order['filled']}")

避坑指南

我在实际项目中遇到过不少坑，这里分享几个最常见的：

  • 数据去重：WebSocket 偶尔会重推数据，尤其是网络波动时。我建议你用交易哈希或者订单 ID 做去重，避免重复处理。
  • 心跳保活：长时间没有数据推送，连接可能会被断开。我一般每 30 秒发一次 ping，确保连接一直活着。
  • 重连机制：网络不可能永远稳定。我建议你写一个自动重连的逻辑，断开后自动重新订阅。
核心要点： 实时数据流是量化交易的基石。成交流让你感知市场脉搏，订单状态推送让你掌控自己的仓位。两者结合，你的策略才能真正做到「眼疾手快」。
