第5章：签名机制详解——EIP-712 结构化数据签名

说到 Hyperliquid 的对接，签名机制是绕不开的核心环节。我个人觉得，这也是最容易踩坑的地方之一。你想想看，一条交易指令从你的程序发出，到链上执行，中间怎么证明「是你发的」？靠的就是签名。

Hyperliquid 用的是 EIP-712 标准。说白了，就是把要签名的数据整理成一个结构化的格式，而不是一串乱七八糟的十六进制。这样做的好处很明显——用户在钱包里签名时，能看到清晰的数据内容，而不是一堆看不懂的哈希。

5.1 为什么是 EIP-712？

我记得最早做 DeFi 项目时，大家还在用 eth_sign。那个方法太原始了，直接对一段字节签名，用户根本不知道自己在签什么。后来出了 EIP-712，才算是解决了这个痛点。

EIP-712 的核心思想是：

  • 定义清晰的数据结构（TypedData）
  • 包含一个 domain 字段，防止跨应用重放攻击
  • 钱包可以解析并展示给用户看

Hyperliquid 选择 EIP-712，也是看中了它的安全性和可读性。你在签名时，钱包里会显示「你要签署一笔订单，金额 xxx，过期时间 xxx」，而不是一串乱码。

重要概念： EIP-712 签名包含三个部分——domain、types 和 message。domain 标识应用，types 定义数据结构，message 是实际数据。

5.2 TypedData 的构建

我们先看一个 Hyperliquid 订单签名的 TypedData 结构。嗯，这里要注意，不同版本的 API 可能略有差异，但核心逻辑是一样的。

5.3 eth_signTypedData_v4 的实现

现在我们来写实际的签名代码。我个人习惯用 eth_account 库，它原生支持 EIP-712。

from eth_account.messages import encode_typed_data
from eth_account import Account
import json

def sign_hyperliquid_order(private_key, order_data, domain_data):
    """
    对 Hyperliquid 订单进行 EIP-712 签名
    
    Args:
        private_key: 私钥（十六进制字符串）
        order_data: 订单数据字典
        domain_data: domain 数据字典
    
    Returns:
        签名结果（十六进制字符串）
    """
    # 构建完整的 TypedData
    typed_data = {
        "types": {
            "EIP712Domain": [
                {"name": "name", "type": "string"},
                {"name": "version", "type": "string"},
                {"name": "chainId", "type": "uint256"},
                {"name": "verifyingContract", "type": "address"}
            ],
            "Order": [
                {"name": "asset", "type": "int32"},
                {"name": "isBuy", "type": "bool"},
                {"name": "reduceOnly", "type": "bool"},
                {"name": "limitPx", "type": "int64"},
                {"name": "sz", "type": "int64"},
                {"name": "orderType", "type": "int32"},
                {"name": "cloid", "type": "bytes16"},
                {"name": "expiration", "type": "uint64"},
                {"name": "salt", "type": "uint256"}
            ]
        },
        "domain": domain_data,
        "primaryType": "Order",
        "message": order_data
    }
    
    # 编码并签名
    encoded = encode_typed_data(full_message=typed_data)
    signed = Account.sign_message(encoded, private_key)
    
    return signed.signature.hex()

# 使用示例
private_key = "0x你的私钥"
domain = {
    "name": "Hyperliquid",
    "version": "1.0",
    "chainId": 42161,
    "verifyingContract": "0x0000000000000000000000000000000000000000"
}

order = {
    "asset": 0,
    "isBuy": True,
    "reduceOnly": False,
    "limitPx": 50000,
    "sz": 100,
    "orderType": 2,
    "cloid": "0x" + "00" * 16,
    "expiration": 1700000000,
    "salt": 123456789
}

signature = sign_hyperliquid_order(private_key, order, domain)
print(f"签名结果: {signature}")
小技巧： 如果你用的是 web3.py，可以用 w3.eth.sign_typed_data() 方法。但 eth_account 更轻量，适合在服务端使用。

5.4 签名验证流程

签名发出去之后，Hyperliquid 服务端会做两件事：

  1. 从签名中恢复出公钥/地址
  2. 检查这个地址是否有权限执行该操作

我们也可以自己验证签名，方便调试：

from eth_account.messages import encode_typed_data
from eth_account import Account

def verify_hyperliquid_signature(signature_hex, order_data, domain_data, expected_address):
    """
    验证 Hyperliquid 订单签名
    
    Args:
        signature_hex: 签名字符串
        order_data: 订单数据
        domain_data: domain 数据
        expected_address: 期望的签名者地址
    
    Returns:
        布尔值，表示签名是否有效
    """
    typed_data = {
        "types": {
            "EIP712Domain": [
                {"name": "name", "type": "string"},
                {"name": "version", "type": "string"},
                {"name": "chainId", "type": "uint256"},
                {"name": "verifyingContract", "type": "address"}
            ],
            "Order": [
                {"name": "asset", "type": "int32"},
                {"name": "isBuy", "type": "bool"},
                {"name": "reduceOnly", "type": "bool"},
                {"name": "limitPx", "type": "int64"},
                {"name": "sz", "type": "int64"},
                {"name": "orderType", "type": "int32"},
                {"name": "cloid", "type": "bytes16"},
                {"name": "expiration", "type": "uint64"},
                {"name": "salt", "type": "uint256"}
            ]
        },
        "domain": domain_data,
        "primaryType": "Order",
        "message": order_data
    }
    
    encoded = encode_typed_data(full_message=typed_data)
    recovered = Account.recover_message(encoded, signature=signature_hex)
    
    return recovered.lower() == expected_address.lower()

5.5 常见坑点与避坑指南

我曾经在签名上栽过跟头，分享几个血泪教训：

坑点1：cloid 的格式

cloid 是 bytes16 类型，必须正好 16 字节。如果你传了 15 字节或 17 字节，签名会失败。我建议用 uuid 生成，然后转成 bytes。

坑点2：int64 的精度

Python 的 int 是无限精度的，但 Hyperliquid 要求 int64。如果你传的值超出范围，签名虽然能生成，但服务端会拒绝。记得做范围检查。

坑点3：chainId 的选择

主网是 42161（Arbitrum），测试网是 421613。我见过有人用错了 chainId，签名一直通不过，排查了半天才发现是这个问题。

5.7 实战建议

最后给你几个实战建议：

  • 先写测试代码：用测试网调试签名逻辑，确认没问题再上主网
  • 保存原始数据：签名时把完整的 TypedData 存下来，方便后续排查问题
  • 注意时间戳：expiration 字段用 Unix 时间戳，单位是秒。我习惯加一个 5 分钟的缓冲
  • salt 要随机：每次签名用不同的 salt，防止重放攻击
我的习惯： 我会把签名逻辑封装成一个独立的模块，然后写单元测试。这样每次改代码时跑一下测试，心里踏实。

好了，EIP-712 签名这块就讲到这里。你只要照着上面的代码写，应该不会出大问题。如果遇到奇怪的签名错误，先检查 cloid 长度和 chainId，这两个是最高频的坑。
