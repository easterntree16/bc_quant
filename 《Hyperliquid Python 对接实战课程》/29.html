第二十九章：测试与调试——单元测试、模拟交易环境、回测引擎集成

说实话，很多做量化的人对测试这件事不太上心。我见过不少团队，代码写完了直接丢到主网上跑，结果爆仓了才发现是某个边界条件没处理。嗯，这种教训一次就够了。

测试不是可有可无的环节。它是你交易系统的安全网。今天我就带你看看，在Hyperliquid生态里，怎么把测试这件事做到位。

单元测试：给每个函数上保险

单元测试听起来高大上，说白了就是验证每个小函数对不对。我个人习惯是，每写一个核心函数，立刻补上对应的测试。别等代码堆到上千行再回头测，那时候你连bug在哪都找不到。

在Hyperliquid的对接中，有几个地方特别容易出问题：

  • 签名计算：私钥签名错了，交易直接失败
  • 订单参数：价格精度、数量精度搞混了
  • 时间戳处理：毫秒和微秒的转换

我建议你用pytest来写测试。它比unittest简洁得多。来看个例子：

# test_order.py
import pytest
from hyperliquid_api import OrderBuilder

def test_limit_order_creation():
    """测试限价单创建"""
    builder = OrderBuilder()
    order = builder.create_limit_order(
        symbol="BTC-USD",
        side="buy",
        price=50000.50,
        size=0.1
    )
    
    assert order["type"] == "limit"
    assert order["price"] == "50000.5"  # 注意精度处理
    assert order["size"] == "0.1"
    assert "signature" in order

def test_invalid_price_raises():
    """测试无效价格是否抛出异常"""
    builder = OrderBuilder()
    with pytest.raises(ValueError):
        builder.create_limit_order(
            symbol="BTC-USD",
            side="buy",
            price=-1,  # 负数价格
            size=0.1
        )
小技巧：测试命名用test_开头，pytest会自动发现。我习惯把测试文件和源码放同一目录，加个tests文件夹。

我在项目中遇到过一个问题：某个订单签名函数在本地测试全过，但一上主网就报错。查了半天，发现是测试环境用的私钥格式不对。所以记住——测试数据要尽量贴近真实环境。

模拟交易环境：不花钱的试错机会

单元测试只能测单个函数。但交易系统是个整体，你需要一个模拟环境来跑完整流程。Hyperliquid提供了测试网，这玩意儿你一定要用。

测试网和主网的区别其实不大：

特性 主网 测试网
资金 真金白银 测试代币（免费领）
API地址 api.hyperliquid.xyz api.testnet.hyperliquid.xyz
撮合速度 真实市场速度 稍慢，但够用
数据 真实行情 模拟行情

怎么切换？很简单。我一般会在配置里加个环境变量：

import os

HYPERLIQUID_CONFIG = {
    "mainnet": {
        "api_url": "https://api.hyperliquid.xyz",
        "ws_url": "wss://api.hyperliquid.xyz/ws"
    },
    "testnet": {
        "api_url": "https://api.testnet.hyperliquid.xyz",
        "ws_url": "wss://api.testnet.hyperliquid.xyz/ws"
    }
}

# 通过环境变量控制
env = os.getenv("HYPER_ENV", "testnet")
config = HYPERLIQUID_CONFIG[env]
警告：千万不要把主网的API密钥硬编码在代码里。我曾经见过有人把私钥写在配置文件里，然后不小心提交到了GitHub...那画面太美我不敢看。

在测试网上跑模拟交易时，我建议你至少跑满100笔订单。为什么？因为很多bug在少量交易时不会暴露，比如订单簿深度变化时的滑点计算、批量撤单的并发问题。

回测引擎集成：用历史数据检验策略

模拟环境只能测当前行情。但你的策略能不能赚钱，得看它在历史数据上的表现。这就是回测的价值。

回测引擎的核心逻辑其实不复杂：

  1. 加载历史K线数据
  2. 逐根K线模拟交易
  3. 记录每笔交易的盈亏
  4. 输出统计指标（夏普比率、最大回撤等）

核心要点：回测时一定要考虑交易成本。Hyperliquid的费率是maker -0.0001，taker 0.0005。别小看这点费用，高频交易时它能吃掉你一半利润。

你想想看，如果回测时每笔交易都按理想价格成交，那结果肯定好看。但实际市场里，你的订单可能吃不到那个价格。所以我建议在回测里加一个滑点模型：

def apply_slippage(price, side, slippage_bps=2):
    """应用滑点，bps表示基点，1bps=0.01%"""
    slippage = price * slippage_bps / 10000
    if side == "buy":
        return price + slippage  # 买入时价格变高
    else:
        return price - slippage  # 卖出时价格变低

我曾经用这个回测框架跑过一个网格策略。回测结果年化30%，我兴冲冲上了主网。结果一个月下来只赚了8%。为什么？因为回测时我没考虑网络延迟和API限频。所以记住——回测是参考，不是承诺。

测试流程的完整闭环

说了这么多，我把整个测试流程串起来。这是我个人比较推崇的做法：

这个闭环的核心思想是：先小后大，先模拟后真实。单元测试过了，才进模拟环境；模拟环境跑通了，才做回测；回测结果满意了，才上主网。每一步都可能发现新问题，发现了就回去改，改完重新测。

我的习惯：每次修改代码后，至少跑一遍完整的测试套件。我写了个Makefile，一个make test命令就能跑完所有测试。省心。

最后说一句：测试不是浪费时间。它是在帮你省钱。你想想看，一个bug如果在单元测试阶段被发现，修复成本几乎为零。但如果到了主网上才发现，那可能就是几万U的损失。这笔账，你自己算。
