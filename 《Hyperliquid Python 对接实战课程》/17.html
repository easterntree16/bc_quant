第十七章：日志与监控：Python logging 配置、关键操作日志记录、异常告警集成

做量化交易，尤其是对接 Hyperliquid 这种链上衍生品协议，最怕什么？

怕程序跑着跑着突然崩了，你却不知道它死在了哪一步。

怕仓位明明该平了，结果因为网络波动没发出去，你还在那傻等。

怕半夜三点被电话叫醒，说你的机器人爆仓了——而你连个日志都没留下。

嗯，这些坑我基本都踩过。所以今天这章，咱们就聊聊怎么把日志和监控这件事做扎实。说白了，就是给你的交易系统装个「黑匣子」和「报警器」。

17.1 为什么日志对量化交易如此重要？

我个人习惯，写任何交易代码之前，先把日志框架搭好。为什么？

  • 故障定位：程序出错了，日志是第一现场。没有日志，你只能靠猜。
  • 交易审计：每一笔下单、撤单、成交，都应该有记录。这是合规和复盘的基础。
  • 性能分析：API 响应慢了？网络延迟高了？日志里的时间戳会告诉你真相。
  • 异常告警：当系统出现非预期行为时，日志能触发告警，让你第一时间介入。

我在项目中遇到过最惨的一次，是某个策略在凌晨两点因为 Hyperliquid 的 gas 价格波动导致交易失败，但程序没有记录任何错误信息。第二天早上我看到账户里多了一堆没平掉的仓位，差点没背过气去。从那以后，我定了个规矩：所有关键操作，必须写日志。

17.2 Python logging 模块基础配置

Python 自带的 logging 模块其实够用，但很多人用错了。最常见的错误是直接 print() 来调试，这在生产环境里就是灾难。

先看一个标准配置：

import logging
import sys
from logging.handlers import RotatingFileHandler

def setup_logger(name: str = "hyperliquid_bot", log_file: str = "trading.log"):
    logger = logging.getLogger(name)
    logger.setLevel(logging.DEBUG)  # 全局级别，但后面 handler 可以覆盖

    # 格式：时间 - 日志级别 - 模块名 - 消息
    formatter = logging.Formatter(
        '%(asctime)s - %(levelname)s - %(name)s - %(message)s'
    )

    # 控制台输出：INFO 及以上
    console_handler = logging.StreamHandler(sys.stdout)
    console_handler.setLevel(logging.INFO)
    console_handler.setFormatter(formatter)

    # 文件输出：DEBUG 及以上，带滚动
    file_handler = RotatingFileHandler(
        log_file, maxBytes=10*1024*1024, backupCount=5
    )
    file_handler.setLevel(logging.DEBUG)
    file_handler.setFormatter(formatter)

    logger.addHandler(console_handler)
    logger.addHandler(file_handler)

    return logger

# 使用
logger = setup_logger()
logger.info("交易系统启动成功")
logger.debug("当前账户余额: 1234.56 USDC")

这里有几个要点：

  • 双输出：控制台看实时信息，文件存完整记录。我习惯控制台只打 INFO 以上，文件里保留 DEBUG。
  • 滚动文件：交易日志增长很快，一天可能几百 MB。设置 maxBytes 和 backupCount 避免磁盘撑爆。
  • 格式化：时间戳精确到毫秒，方便后续分析延迟。
我的小技巧：日志文件名里带上日期，比如 trading_2025-01-15.log。这样按天归档，查找历史记录特别方便。

17.3 关键操作日志记录：该记什么？

不是所有东西都要记。记太多日志会影响性能，记太少又查不出问题。我总结了一套「关键操作清单」：

操作类型 日志级别 记录内容
系统启动/关闭 INFO 启动时间、配置参数、版本号
下单请求 INFO 交易对、方向、数量、价格、订单类型
订单成交 INFO 订单ID、成交价、成交量、手续费
撤单操作 INFO 订单ID、撤单原因（如超时）
API 错误 ERROR 错误码、错误消息、请求参数
网络异常 WARNING 重试次数、当前延迟、异常类型
风控触发 CRITICAL 风控规则、当前持仓、触发阈值

举个例子，下单时的日志应该这样写：

def place_order(symbol: str, side: str, size: float, price: float):
    logger.info(f"下单请求 | 交易对={symbol} | 方向={side} | 数量={size} | 价格={price}")
    try:
        # 调用 Hyperliquid API
        response = hyperliquid_client.order(symbol, side, size, price)
        if response.get("status") == "ok":
            logger.info(f"下单成功 | 订单ID={response['order_id']} | 成交价={response['filled_price']}")
        else:
            logger.error(f"下单失败 | 错误={response.get('error')} | 参数={symbol},{side},{size},{price}")
    except Exception as e:
        logger.exception(f"下单异常 | 交易对={symbol} | 异常类型={type(e).__name__}")

注意这里用了 logger.exception()，它会自动把完整的堆栈信息打出来。这个在调试时特别有用。

避坑指南：千万不要在日志里记录私钥、API Secret 等敏感信息。我曾经见过有人把私钥直接打在日志里，然后日志文件被上传到 GitHub……后果你懂的。

17.4 异常告警集成：从日志到通知

光有日志还不够。你不可能 24 小时盯着控制台看。所以我们需要把日志和告警系统打通。

常见的告警方式：

  • 邮件：适合非紧急告警，比如每日交易总结。
  • 企业微信/钉钉/Slack：适合实时告警，比如风控触发。
  • 短信/电话：适合最高级别告警，比如账户异常。

我一般用 Webhook 的方式集成。以企业微信为例：

import requests
import json

class WeChatBotHandler(logging.Handler):
    def __init__(self, webhook_url: str, level=logging.WARNING):
        super().__init__(level)
        self.webhook_url = webhook_url

    def emit(self, record: logging.LogRecord):
        # 只发送 WARNING 及以上级别的日志
        if record.levelno < self.level:
            return
        log_entry = self.format(record)
        payload = {
            "msgtype": "text",
            "text": {
                "content": f"[{record.levelname}] {log_entry}"
            }
        }
        try:
            requests.post(self.webhook_url, json=payload, timeout=5)
        except Exception as e:
            # 告警发送失败本身也要记录
            print(f"发送告警失败: {e}")

# 集成到 logger
webhook_url = "https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=YOUR_KEY"
wechat_handler = WeChatBotHandler(webhook_url, level=logging.WARNING)
logger.addHandler(wechat_handler)

这样配置之后，只要日志级别达到 WARNING 或以上，就会自动推送到你的企业微信群。我自己的机器人，风控触发时还会直接打电话给我——当然，那是另一个故事了。

你看，日志不只是「记下来」，它要能驱动后续的动作。从采集、存储、分析到告警，形成一个完整的闭环。只有这样，你的交易系统才算真正「上了保险」。

17.6 实战中的几个小建议

  1. 日志级别要合理：DEBUG 用于开发调试，INFO 用于正常流程，WARNING 用于潜在问题，ERROR 用于可恢复的错误，CRITICAL 用于不可恢复的灾难。别把 INFO 当 DEBUG 用，也别把 ERROR 当 INFO 用。
  2. 结构化日志：如果条件允许，用 JSON 格式记录日志。这样后续用 ELK 或 Splunk 分析时，可以直接按字段搜索。
  3. 告警要分级：不是所有错误都需要半夜叫醒你。网络超时可以重试，发个 WARNING 就行；但风控触发必须立刻处理，用 CRITICAL 级别。
  4. 定期检查日志：日志系统本身也会出问题。比如磁盘满了、权限不对、Webhook 失效。我每周会花 10 分钟检查日志是否正常写入。

核心总结：日志是交易系统的「黑匣子」，告警是「救生圈」。没有日志，你无法复盘；没有告警，你无法及时止损。这两样东西，花再多时间搭建都值得。

好了，这章的内容就到这里。记住，写日志不是写给别人看的，是写给未来的自己看的。你永远不知道明天会遇到什么 bug，但有了完善的日志和告警，至少你不会在黑暗中摸索。
