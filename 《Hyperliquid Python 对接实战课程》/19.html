策略框架搭建（一）：策略基类设计、回测与实盘模式切换

做量化交易，说白了就是跟不确定性打交道。我见过太多人一上来就写策略逻辑，结果回测和实盘跑出来的数据完全对不上。嗯，这里有个核心问题——策略框架没搭好。

我个人习惯，先设计一个策略基类。所有策略都从这个基类继承。这样回测和实盘只需要切换一个参数，代码复用率极高。今天我们就来聊聊这个基类怎么设计，以及模式切换的坑怎么填。

为什么需要策略基类？

你想想看，一个策略在回测时，需要历史数据、模拟撮合、计算盈亏。到了实盘，需要连接交易所、处理实时行情、管理订单状态。这两者的逻辑完全不同，但策略的核心信号生成逻辑是一样的。

我在项目中遇到过，有人把回测和实盘写成了两套代码。结果回测赚了30%，实盘亏了20%。为什么？因为两套代码的细节处理不一致。比如滑点、手续费、订单类型，稍微差一点，结果就天差地别。

所以，基类的核心作用就是：把策略的信号生成逻辑固定下来，把回测和实盘的差异封装到子类或配置中。

策略基类的核心设计

我们先看一个精简版的基类设计。这个基类包含了策略生命周期的主要方法。

from abc import ABC, abstractmethod
from enum import Enum

class Mode(Enum):
    BACKTEST = "backtest"
    LIVE = "live"

class BaseStrategy(ABC):
    def __init__(self, mode: Mode, config: dict):
        self.mode = mode
        self.config = config
        self.position = 0
        self.capital = config.get("initial_capital", 10000)
        self.trades = []

    @abstractmethod
    def on_data(self, data):
        """处理每一条行情数据，生成交易信号"""
        pass

    def on_order(self, order):
        """订单状态更新回调"""
        pass

    def on_trade(self, trade):
        """成交回调"""
        self.trades.append(trade)
        self.position += trade.quantity

    def calculate_pnl(self):
        """计算当前盈亏"""
        return sum(t.pnl for t in self.trades)

    def run(self):
        """启动策略，根据模式选择执行逻辑"""
        if self.mode == Mode.BACKTEST:
            self._run_backtest()
        elif self.mode == Mode.LIVE:
            self._run_live()

    def _run_backtest(self):
        """回测模式：从历史数据循环"""
        raise NotImplementedError

    def _run_live(self):
        """实盘模式：连接交易所，订阅行情"""
        raise NotImplementedError

这个基类有几个关键点：

  • Mode 枚举：明确区分回测和实盘模式
  • 抽象方法 on_data：子类必须实现，这是策略的核心
  • 生命周期回调：on_order、on_trade 等，方便扩展
  • run 方法：根据模式自动选择执行路径
我的小技巧：在 on_data 里只做信号判断，不要直接下单。把下单逻辑放到另一个方法里。这样回测时可以模拟撮合，实盘时可以调用交易所 API。职责单一，调试起来也方便。

回测与实盘模式切换

模式切换的核心，其实就是一句话：同一个策略，不同的执行引擎。

回测时，我们用一个循环遍历历史数据，模拟市场环境。实盘时，我们连接 WebSocket，实时接收行情。但策略的 on_data 方法，接收的数据格式应该保持一致。

我曾经犯过一个错误：回测时数据是 pandas DataFrame，实盘时数据是字典。结果 on_data 里写了一大堆 if-else 来判断数据类型。后来我统一了数据格式，用 NamedTuple 或者简单的 dataclass，问题就解决了。

from dataclasses import dataclass

@dataclass
class MarketData:
    symbol: str
    timestamp: int
    price: float
    volume: float
    bid: float
    ask: float

这样，无论回测还是实盘，on_data 接收的都是 MarketData 对象。代码干净，逻辑清晰。

一个完整的策略示例

我们写一个简单的移动平均线策略，继承自 BaseStrategy。

class MovingAverageStrategy(BaseStrategy):
    def __init__(self, mode, config):
        super().__init__(mode, config)
        self.short_window = config.get("short_window", 5)
        self.long_window = config.get("long_window", 20)
        self.prices = []

    def on_data(self, data: MarketData):
        self.prices.append(data.price)
        if len(self.prices) < self.long_window:
            return

        short_ma = sum(self.prices[-self.short_window:]) / self.short_window
        long_ma = sum(self.prices[-self.long_window:]) / self.long_window

        if short_ma > long_ma and self.position == 0:
            self._place_order("buy", data.price, 1)
        elif short_ma < long_ma and self.position > 0:
            self._place_order("sell", data.price, 1)

    def _place_order(self, side, price, quantity):
        # 回测时直接模拟成交
        if self.mode == Mode.BACKTEST:
            trade = Trade(side, price, quantity)
            self.on_trade(trade)
        # 实盘时调用交易所 API
        elif self.mode == Mode.LIVE:
            # 这里调用 Hyperliquid 的 SDK
            pass
核心思想：on_data 只做信号判断，_place_order 负责执行。这样回测和实盘的差异被隔离在 _place_order 内部。你只需要修改这一个方法，就能切换模式。

配置管理

策略的参数，比如移动平均线的窗口大小、初始资金、手续费率，都应该放在配置文件里。不要硬编码在代码中。

# config.yaml
strategy:
  name: moving_average
  short_window: 5
  long_window: 20
  initial_capital: 10000
  commission: 0.001

mode: backtest
data_path: "./data/btc_usdt.csv"

在 Python 中读取配置，我习惯用 yaml 库。这样修改参数只需要改配置文件，不需要改代码。

import yaml

with open("config.yaml", "r") as f:
    config = yaml.safe_load(f)

mode = Mode(config["mode"])
strategy = MovingAverageStrategy(mode, config["strategy"])
strategy.run()
避坑指南：我曾经把手续费率写死在代码里，结果换了交易所，手续费不同，回测结果完全失真。后来我把所有参数都放到配置文件里，换交易所只需要改一个文件。省心多了。

总结

策略基类设计，说白了就是抽象与隔离。把不变的信号逻辑抽象出来，把变化的执行逻辑隔离出去。这样，你的策略就能在回测和实盘之间无缝切换。

我个人习惯，每次写新策略前，先花10分钟设计基类接口。虽然看起来多花了时间，但后期调试和维护能省下大把时间。你想想看，如果回测和实盘共用一套信号逻辑，出问题的时候，你只需要排查一个地方，而不是两套代码。

嗯，今天就聊到这里。记住：框架搭好了，策略才能跑得稳。
