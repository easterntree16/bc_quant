第28章：部署与运维：Linux服务器部署、Supervisor进程管理、Docker容器化

量化交易系统写好了，策略回测跑通了，实盘接口也调通了。然后呢？

然后就是部署。这一步其实最容易被忽视。我见过太多人，代码写得漂漂亮亮，一上服务器就各种崩。说白了，本地环境和生产环境是两码事。你笔记本上跑得好好的，换到云服务器上可能连数据库都连不上。

今天我们就聊聊怎么把Hyperliquid的量化机器人稳稳当当地部署到Linux服务器上。我会把我在生产环境中踩过的坑、积累的经验，一次性倒出来。

28.1 为什么需要专门的部署方案？

你可能觉得，直接在服务器上开个终端，python bot.py 跑起来不就完了？

嗯，短期可以。但你想过这些问题吗：

  • 终端一关，程序就停了
  • 程序崩溃了没人管，半夜爆仓
  • 服务器重启了，你得手动再跑一遍
  • 依赖环境搞乱了，整个系统废掉

我在2022年刚开始做Hyperliquid策略时，就吃过这个亏。当时图省事，直接在服务器上裸跑。结果有一次服务器自动更新重启，我的做市策略停了整整8个小时。醒来一看，仓位全没了。嗯，从那以后我再也不敢偷懒了。

核心要点：量化交易机器人需要7×24小时稳定运行。部署方案必须解决：进程守护、自动重启、环境隔离、日志管理这四个问题。

28.2 Linux服务器基础配置

先说说服务器选型。我个人习惯用Ubuntu 20.04或22.04 LTS版本。为什么？稳定，社区活跃，遇到问题好搜解决方案。

28.2.1 初始环境准备

拿到一台新服务器，第一件事不是装Python，而是更新系统和安装基础工具：

# 更新系统
sudo apt update && sudo apt upgrade -y

# 安装基础工具
sudo apt install -y git curl wget vim htop net-tools

# 安装Python 3.10+
sudo apt install -y python3.10 python3.10-venv python3.10-dev

# 创建专用用户（不要用root跑交易程序）
sudo useradd -m -s /bin/bash hyperliquid
sudo usermod -aG sudo hyperliquid

我的习惯：永远创建一个专用系统用户来跑交易程序。这样即使程序被攻破，攻击者也拿不到root权限。安全第一。

28.2.2 Python虚拟环境

每个项目都应该有自己的虚拟环境。别把所有依赖装到系统Python里，那是给自己挖坑。

# 切换到专用用户
su - hyperliquid

# 创建项目目录
mkdir -p ~/hyperliquid_bot
cd ~/hyperliquid_bot

# 创建虚拟环境
python3.10 -m venv venv

# 激活虚拟环境
source venv/bin/activate

# 安装依赖
pip install --upgrade pip
pip install hyperliquid-python-sdk
pip install pandas numpy ccxt
pip install python-dotenv
pip install requests websocket-client

你想想看，如果哪天你要升级某个库的版本，或者要跑两个不同依赖版本的项目，虚拟环境就是你的救命稻草。

28.3 Supervisor进程管理

Supervisor是我最常用的进程管理工具。它能把你的Python脚本变成系统服务，自动启动、自动重启、还能看日志。

28.3.1 安装与配置

# 安装Supervisor
sudo apt install -y supervisor

# 创建配置文件
sudo vim /etc/supervisor/conf.d/hyperliquid_bot.conf

配置文件长这样：

[program:hyperliquid_bot]
command=/home/hyperliquid/hyperliquid_bot/venv/bin/python /home/hyperliquid/hyperliquid_bot/main.py
directory=/home/hyperliquid/hyperliquid_bot
user=hyperliquid
autostart=true
autorestart=true
startretries=3
stopasgroup=true
killasgroup=true
stdout_logfile=/var/log/hyperliquid_bot/out.log
stderr_logfile=/var/log/hyperliquid_bot/err.log
stdout_logfile_maxbytes=10MB
stdout_logfile_backups=5
environment=PYTHONPATH="/home/hyperliquid/hyperliquid_bot"

注意：command路径一定要用绝对路径。我遇到过有人用相对路径，结果Supervisor找不到程序，折腾了半天。

28.3.2 常用操作命令

# 重新加载配置
sudo supervisorctl reread
sudo supervisorctl update

# 启动/停止/重启
sudo supervisorctl start hyperliquid_bot
sudo supervisorctl stop hyperliquid_bot
sudo supervisorctl restart hyperliquid_bot

# 查看状态
sudo supervisorctl status

# 查看实时日志
sudo supervisorctl tail -f hyperliquid_bot

Supervisor最爽的一点是：程序崩溃了，它自动帮你重启。我曾经有一次策略里有个小bug，偶尔会触发空指针异常。Supervisor在一天内帮我自动重启了17次，交易愣是没断过。

28.4 Docker容器化

如果说Supervisor解决了进程管理问题，那Docker解决的就是环境一致性问题。

28.4.1 为什么用Docker？

说白了，Docker把你的整个运行环境打包成一个镜像。你本地能跑，服务器就能跑，换台机器照样跑。再也不用担心「我电脑上明明可以的」这种问题了。

28.4.2 Dockerfile编写

# 使用Python 3.10作为基础镜像
FROM python:3.10-slim

# 设置工作目录
WORKDIR /app

# 安装系统依赖
RUN apt-get update && apt-get install -y \
    gcc \
    && rm -rf /var/lib/apt/lists/*

# 复制依赖文件
COPY requirements.txt .

# 安装Python依赖
RUN pip install --no-cache-dir -r requirements.txt

# 复制项目代码
COPY . .

# 创建日志目录
RUN mkdir -p /var/log/hyperliquid_bot

# 设置时区
ENV TZ=Asia/Shanghai
RUN ln -snf /usr/share/zoneinfo/$TZ /etc/localtime && echo $TZ > /etc/timezone

# 运行命令
CMD ["python", "main.py"]

28.4.3 docker-compose.yml

我习惯用docker-compose来管理多个容器。比如你的策略需要同时跑数据库、消息队列，用compose一键搞定。

version: '3.8'

services:
  hyperliquid_bot:
    build: .
    container_name: hyperliquid_bot
    restart: always
    volumes:
      - ./logs:/var/log/hyperliquid_bot
      - ./config:/app/config
    environment:
      - PYTHONUNBUFFERED=1
      - TZ=Asia/Shanghai
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"
    networks:
      - trading_net

networks:
  trading_net:
    driver: bridge

经验之谈：把配置文件通过volume挂载到容器外。这样更新配置时不用重新构建镜像，直接改配置文件然后重启容器就行。

28.4.4 构建与运行

# 构建镜像
docker build -t hyperliquid_bot:v1.0 .

# 启动容器
docker-compose up -d

# 查看日志
docker logs -f hyperliquid_bot

# 进入容器
docker exec -it hyperliquid_bot /bin/bash

# 停止容器
docker-compose down

28.6.1 日志管理

日志是你的第一道防线。程序出问题了，第一件事就是看日志。

import logging
import logging.handlers

# 配置日志轮转
handler = logging.handlers.RotatingFileHandler(
    '/var/log/hyperliquid_bot/trading.log',
    maxBytes=10*1024*1024,  # 10MB
    backupCount=5
)

logging.basicConfig(
    level=logging.INFO,
    format='%(asctime)s - %(name)s - %(levelname)s - %(message)s',
    handlers=[handler]
)

28.6.2 健康检查

我建议在策略里加一个健康检查接口。这样你可以用外部监控工具（比如Prometheus）定期检查程序是否活着。

# 简单的健康检查端点
from flask import Flask, jsonify
import threading

app = Flask(__name__)
last_trade_time = None

@app.route('/health')
def health():
    return jsonify({
        'status': 'ok',
        'last_trade': str(last_trade_time),
        'uptime': time.time() - start_time
    })

def run_health_server():
    app.run(host='0.0.0.0', port=8080)

# 在另一个线程启动
threading.Thread(target=run_health_server, daemon=True).start()

曾经踩过的坑：有一次我忘了在Dockerfile里设置时区，结果日志时间全是UTC。凌晨3点的交易记录显示的是晚上7点，排查问题的时候差点被搞疯。记得一定要设置 TZ=Asia/Shanghai。

28.6.3 安全加固

  • API密钥不要硬编码在代码里，用环境变量或配置文件
  • 配置文件权限设为600，只有程序用户能读
  • 开启防火墙，只开放必要的端口
  • 定期更新系统和依赖包

好了，部署这块就聊这么多。记住一个原则：自动化一切能自动化的东西。手动操作越少，出错的概率就越低。你的量化机器人应该像一台精密的瑞士钟表，默默地在服务器里运转，你只需要偶尔看看日志，确认一切正常就好。
