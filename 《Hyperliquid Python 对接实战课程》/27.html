第二十七章：安全最佳实践——私钥加密存储、环境变量管理、API权限最小化

说实话，做量化交易这几年，我见过太多因为安全问题翻车的案例了。我自己早期也踩过坑——有一次把私钥硬编码在脚本里，结果不小心把代码传到了公开仓库，虽然及时撤回了，但那种后背发凉的感觉，到现在都记得。

今天这章，咱们就聊聊 Hyperliquid 对接中必须重视的三个安全要点：私钥怎么存、环境变量怎么管、API 权限怎么设。说白了，就是让你在赚钱的同时，别把家底儿赔进去。

一、私钥加密存储——别让密钥裸奔

私钥是什么？是你账户的命根子。谁拿到它，谁就能控制你的资金。所以，永远不要把私钥明文写在代码里。

⚠️ 警告： 以下做法极度危险：
  • 在 Python 文件中直接写 PRIVATE_KEY = "0xabc123..."
  • 把私钥放在 Git 仓库里（哪怕私有仓库）
  • 通过命令行参数传递私钥（会被进程列表看到）

我个人习惯的做法是：使用加密文件存储私钥，运行时解密。比如用 cryptography 库对私钥进行 AES 加密，密码从环境变量读取。

from cryptography.fernet import Fernet
import os

# 生成密钥（仅一次）
# key = Fernet.generate_key()
# 保存到环境变量或安全存储

def encrypt_private_key(private_key: str, password: str) -> bytes:
    """加密私钥"""
    f = Fernet(base64.urlsafe_b64encode(password.encode().ljust(32)[:32]))
    return f.encrypt(private_key.encode())

def decrypt_private_key(encrypted_key: bytes, password: str) -> str:
    """解密私钥"""
    f = Fernet(base64.urlsafe_b64encode(password.encode().ljust(32)[:32]))
    return f.decrypt(encrypted_key).decode()

# 使用示例
encrypted = encrypt_private_key("0x你的私钥", os.getenv("DECRYPT_PASSWORD"))
# 将 encrypted 写入文件
with open("encrypted_key.bin", "wb") as f:
    f.write(encrypted)

# 运行时读取
with open("encrypted_key.bin", "rb") as f:
    encrypted_data = f.read()
private_key = decrypt_private_key(encrypted_data, os.getenv("DECRYPT_PASSWORD"))

嗯，这里要注意：加密密码本身也要安全存储。我一般把它放在环境变量里，或者用专门的密钥管理服务（比如 AWS KMS、HashiCorp Vault）。

💡 小技巧： 如果你用的是 Hyperliquid 的 SDK，它支持从环境变量读取私钥。你可以把加密后的私钥放在文件里，启动时解密后注入环境变量，再启动交易程序。

二、环境变量管理——别把配置写死

环境变量是管理敏感配置的标准做法。为什么？因为它不会不小心被提交到 Git 里，也方便在不同环境（开发、测试、生产）之间切换。

我建议你使用 python-dotenv 库来管理环境变量。创建一个 .env 文件，里面放所有敏感信息，然后把这个文件加到 .gitignore 里。

# .env 文件示例
HYPERLIQUID_PRIVATE_KEY=0x你的私钥
HYPERLIQUID_WALLET_ADDRESS=0x你的地址
DECRYPT_PASSWORD=你的解密密码
RPC_URL=https://api.hyperliquid.xyz
LOG_LEVEL=INFO

# 在代码中加载
from dotenv import load_dotenv
import os

load_dotenv()  # 加载 .env 文件

private_key = os.getenv("HYPERLIQUID_PRIVATE_KEY")
wallet_address = os.getenv("HYPERLIQUID_WALLET_ADDRESS")
rpc_url = os.getenv("RPC_URL")

我曾经犯过一个错：把 .env 文件放在了项目根目录，结果有一次打包时忘了排除它，差点把生产环境的配置泄露出去。后来我学乖了，把 .env 放在项目外的一个安全目录，启动时通过参数指定路径。

✅ 最佳实践清单：
  • 所有敏感信息都走环境变量，不硬编码
  • .env 文件永远不要提交到 Git
  • 不同环境使用不同的 .env 文件（如 .env.dev、.env.prod）
  • 生产环境使用密钥管理服务，而不是文件
  • 定期轮换密钥和密码

三、API 权限最小化——够用就行，别给太多

Hyperliquid 的 API 权限设计其实挺清晰的。你想想看，如果你的交易机器人只需要读取行情和下单，那它就不应该有提现权限。这就是「最小权限原则」的核心思想。

在 Hyperliquid 中，权限主要通过钱包签名来控制。不同的操作需要不同的签名权限：

操作类型 所需权限 说明
查询余额、订单簿 只读（无需签名） 公开数据，不需要私钥
下单、撤单 交易签名 需要私钥签名交易
提现、转账 提现签名 需要额外授权，建议单独管理
合约部署、管理 管理员权限 仅用于开发阶段，生产环境禁用

我建议你为不同的用途创建不同的钱包：

  • 交易钱包：只存交易所需资金，权限只给下单和查询
  • 资金钱包：存大部分资产，不参与交易，权限只给转账
  • 开发钱包：用测试网，随便折腾

这样做的好处是：即使交易钱包的私钥泄露了，攻击者也最多只能操作交易账户里的资金，动不了你的大本营。

⚠️ 特别注意： 永远不要在交易机器人中使用提现权限。如果你需要手动提现，用另一个工具或脚本，单独授权。我见过有人把提现和交易逻辑写在一起，结果一个 bug 导致资金被转走——虽然最后找回来了，但过程极其痛苦。
