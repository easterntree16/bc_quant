项目实战：从零搭建一个完整的 Hyperliquid 量化交易机器人

说实话，很多朋友学完 API 调用、订单管理、WebSocket 这些零散知识点后，最常问我的问题是：「老哥，这些东西怎么串起来？」

嗯，今天我们就来干这件事。从零开始，完整搭建一个能跑在 Hyperliquid 上的量化交易机器人。我会带着你走完需求分析、架构设计、编码实现、部署上线这四个阶段。

我个人习惯，做项目前先画一张图，把脑子里的想法倒出来。下面这张图就是我们整个机器人的核心逻辑：

1. 需求分析：先想清楚要做什么

做量化交易机器人，最忌讳的就是「先写代码再说」。我见过太多人，写了三天代码，最后发现需求都没想清楚。

我们这次的目标很明确：

  • 交易标的：BTC-USD 永续合约
  • 策略类型：基于 EMA 均线交叉的趋势跟踪策略
  • 运行模式：24/7 无人值守，但要有手动干预接口
  • 风险控制：单笔最大亏损 2%，总仓位不超过 30%

核心需求清单：

  1. 实时获取 BTC 的 tick 级行情数据
  2. 计算 5 分钟和 20 分钟 EMA 均线
  3. 金叉开多，死叉开空，反向信号平仓
  4. 支持止损单和止盈单
  5. 所有操作记录日志，方便复盘
  6. 异常情况自动熔断，停止交易

嗯，这里要注意一点：需求不是越复杂越好。我刚开始做的时候，总想塞一堆指标进去，结果策略反而跑崩了。简单的东西往往更可靠。

2. 架构设计：分层解耦，各司其职

架构设计说白了，就是怎么把代码组织得「好改、好测、好扩展」。我个人习惯用三层架构：数据层、策略层、执行层。

层级 职责 核心组件
数据层 行情获取、数据缓存、K线合成 WebSocket 客户端、Redis 缓存
策略层 信号计算、风险管理、决策生成 EMA 计算器、风控模块
执行层 订单发送、状态跟踪、错误处理 订单管理器、重试队列

为什么这么分？我在项目中遇到过一个问题：一开始把行情处理和策略计算写在一起，结果行情数据格式一变，整个代码都得改。分层之后，改数据层不影响策略层，改策略层不影响执行层。说白了，就是「解耦」。

小技巧：每一层都定义清晰的接口。比如数据层只输出统一的 OHLCV 结构，策略层只接收这个结构，不关心数据是从 WebSocket 来的还是从 CSV 文件读的。这样后期换数据源，改一行代码就行。

3. 编码实现：从核心模块开始写

编码阶段，我习惯先写核心逻辑，再写外围代码。核心逻辑就是策略信号生成和订单管理。

3.1 数据层实现

先搞定行情数据。我们用 WebSocket 订阅实时 tick，然后合成 1 分钟 K 线。

import asyncio
import json
import websockets
from collections import deque

class DataFeed:
    def __init__(self):
        self.ws_url = "wss://api.hyperliquid.xyz/ws"
        self.tick_buffer = deque(maxlen=1000)  # 缓存最近的 tick
        self.minute_bars = deque(maxlen=100)   # 缓存最近的 K 线

    async def connect(self):
        async with websockets.connect(self.ws_url) as ws:
            # 订阅 BTC 的 trade 数据
            subscribe_msg = {
                "type": "subscribe",
                "channel": "trades",
                "coin": "BTC"
            }
            await ws.send(json.dumps(subscribe_msg))
            
            async for message in ws:
                data = json.loads(message)
                if data.get("channel") == "trades":
                    self._process_tick(data["data"])
    
    def _process_tick(self, tick):
        self.tick_buffer.append(tick)
        # 这里可以合成 K 线，代码略
        pass

这段代码看着简单，但有个坑：WebSocket 断连怎么办？我曾经在生产环境遇到过，WebSocket 断开后没重连，机器人傻傻地以为市场没波动，一直不开仓。后来我加了心跳检测和自动重连机制。

3.2 策略层实现

EMA 均线交叉策略，代码其实不长：

import pandas as pd
import numpy as np

class EMACrossStrategy:
    def __init__(self, fast_period=5, slow_period=20):
        self.fast_period = fast_period
        self.slow_period = slow_period
        self.position = 0  # 0: 空仓, 1: 多头, -1: 空头

    def calculate_ema(self, prices, period):
        return prices.ewm(span=period, adjust=False).mean()

    def generate_signal(self, df):
        # df 必须包含 'close' 列
        fast_ema = self.calculate_ema(df['close'], self.fast_period)
        slow_ema = self.calculate_ema(df['close'], self.slow_period)
        
        current_fast = fast_ema.iloc[-1]
        current_slow = slow_ema.iloc[-1]
        prev_fast = fast_ema.iloc[-2]
        prev_slow = slow_ema.iloc[-2]
        
        # 金叉：快线上穿慢线
        if prev_fast <= prev_slow and current_fast > current_slow:
            return 'BUY'
        # 死叉：快线下穿慢线
        elif prev_fast >= prev_slow and current_fast < current_slow:
            return 'SELL'
        else:
            return 'HOLD'

注意：EMA 计算需要足够的历史数据。如果 K 线数据不够 20 根，算出来的 EMA 是不准的。我建议至少缓存 50 根 K 线再开始交易。

3.3 执行层实现

订单管理这块，核心是处理订单状态。Hyperliquid 的订单有 pending、filled、cancelled 三种状态。我们需要一个状态机来跟踪。

class OrderManager:
    def __init__(self, exchange):
        self.exchange = exchange
        self.active_orders = {}  # order_id -> order_info

    async def place_order(self, side, size, price=None, order_type='market'):
        # 构造订单
        order = {
            'side': side,
            'size': size,
            'price': price,
            'order_type': order_type
        }
        
        # 发送到交易所
        response = await self.exchange.place_order(order)
        order_id = response['order_id']
        
        # 记录到本地
        self.active_orders[order_id] = {
            'order': order,
            'status': 'pending',
            'timestamp': time.time()
        }
        
        return order_id

    async def check_order_status(self, order_id):
        # 轮询或通过 WebSocket 获取状态
        status = await self.exchange.get_order_status(order_id)
        self.active_orders[order_id]['status'] = status
        
        if status == 'filled':
            # 触发后续逻辑：更新仓位、记录日志
            await self._on_order_filled(order_id)
        elif status == 'cancelled':
            # 清理记录
            del self.active_orders[order_id]

这里有个经验：不要频繁轮询订单状态。Hyperliquid 的 API 有频率限制，我一般用 WebSocket 监听订单更新事件，比轮询快得多，还不占额度。

4. 部署上线：让机器人跑起来

代码写完了，怎么让它 24 小时跑？我推荐用 Docker 部署，简单又稳定。

4.1 Docker 化

# Dockerfile
FROM python:3.10-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["python", "main.py"]

4.2 启动脚本

# docker-compose.yml
version: '3.8'
services:
  bot:
    build: .
    environment:
      - HYPERLIQUID_PRIVATE_KEY=${PRIVATE_KEY}
      - HYPERLIQUID_WALLET=${WALLET_ADDRESS}
    volumes:
      - ./logs:/app/logs
    restart: always

部署小贴士：私钥千万别写死在代码里！用环境变量或者 .env 文件。我曾经见过有人把私钥传到 GitHub 上，那画面太美我不敢看。

4.3 监控与告警

机器人跑起来后，不能就不管了。我一般加三个监控：

  • 日志监控：记录每次交易决策和订单结果
  • 资金监控：每小时检查一次账户权益，异常波动发告警
  • 心跳监控：每 5 分钟检查 WebSocket 是否还连着

告警我用的是 Telegram Bot，简单免费。代码大概这样：

import requests

def send_alert(message):
    bot_token = "YOUR_BOT_TOKEN"
    chat_id = "YOUR_CHAT_ID"
    url = f"https://api.telegram.org/bot{bot_token}/sendMessage"
    requests.post(url, json={"chat_id": chat_id, "text": message})

5. 总结与避坑

好了，整个流程走完了。从需求分析到架构设计，再到编码和部署，每一步都有它的道理。我最后给你几个避坑指南：

  • 回测再上线：别直接拿真金白银试。先用历史数据回测，再用小资金跑模拟盘。
  • 熔断机制必须有：连续亏损 3 笔，自动停止交易。我见过有人一天亏掉 30% 还不止损的。
  • 日志要详细：每个订单的发送时间、成交价格、滑点都要记。复盘的时候你就知道这有多重要了。
  • 网络波动要处理：Hyperliquid 的 API 偶尔会超时，加个重试机制，最多重试 3 次，超过就熔断。

做量化交易，说白了就是「活得久比赚得快更重要」。代码写得再漂亮，风控没做好，一切都是白搭。希望这个实战项目能帮你少走一些弯路。
