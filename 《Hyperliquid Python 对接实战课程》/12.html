第十二章：WebSocket 基础：连接建立、心跳维持、订阅与取消订阅

好，咱们进入 WebSocket 的世界。

说实话，做量化交易，尤其是高频策略，延迟就是金钱。REST API 那种一问一答的模式，在行情瞬息万变的时候，根本跟不上节奏。你想想看，你刚问完价格，下一秒可能已经变了。所以，我们需要 WebSocket——一个全双工的、低延迟的通信通道。

我个人习惯把 WebSocket 比作「一根一直通着的电话线」。你拨通之后，不用每次说话都重新拨号。交易所那边有行情变化，直接通过这根线推给你。这就是它的核心价值：实时推送。

12.1 连接建立：从零到一

在 Hyperliquid 生态里，建立 WebSocket 连接其实非常直接。我们用的是标准 WebSocket 协议，也就是 wss:// 开头的地址。

我记得第一次对接时，我犯了个低级错误——用了 ws://（非加密）。结果连接一直失败，日志里全是 SSL 错误。后来才意识到，生产环境必须用加密的 wss://。嗯，这里要注意，永远不要在生产环境用非加密连接，数据被截获是小，连接不稳定才是大问题。

核心连接流程：

  1. 客户端发起 HTTP 升级请求（Upgrade: websocket）
  2. 服务端返回 101 Switching Protocols
  3. 连接建立成功，进入全双工通信模式

下面是我常用的 Python 连接代码，用的是 websockets 这个库，非常轻量：

import asyncio
import websockets

async def connect_hyperliquid():
    uri = "wss://api.hyperliquid.xyz/ws"
    async with websockets.connect(uri) as websocket:
        print("连接成功！")
        # 这里可以开始收发消息了
        # 比如接收一条欢迎消息
        response = await websocket.recv()
        print(f"收到: {response}")

asyncio.run(connect_hyperliquid())

这段代码看着简单，但有个细节：websockets.connect 默认会处理自动重连吗？不会。我在项目中遇到过网络抖动，连接突然断了，程序就卡死了。所以，一定要自己实现重连逻辑。后面我会讲到。

12.2 心跳维持：别让连接断了

连接建立后，最怕什么？怕它静默断开。

很多防火墙或代理服务器，会在一段时间没有数据传输后，主动掐掉空闲连接。你想想看，你正等着行情推送呢，结果连接被掐了，数据收不到，策略还在傻傻地跑——这后果很严重。

所以，我们需要心跳机制。说白了，就是定时给服务器发一个「我还活着」的信号。

我的经验：心跳间隔不要设得太短（比如1秒），会增加不必要的网络开销；也不要太长（比如5分钟），容易被中间设备断开。我个人习惯用 30秒 作为心跳间隔。

Hyperliquid 的心跳格式很简单，发送一个 JSON 字符串：

{
  "type": "ping"
}

服务器收到后，会回复一个 pong。如果连续几次没收到 pong，就该考虑重连了。

下面是一个带心跳的完整示例：

import asyncio
import websockets
import json

async def heartbeat(websocket):
    while True:
        try:
            await websocket.send(json.dumps({"type": "ping"}))
            print("发送心跳 ping")
            await asyncio.sleep(30)  # 每30秒发一次
        except websockets.ConnectionClosed:
            print("连接已关闭，停止心跳")
            break

async def main():
    uri = "wss://api.hyperliquid.xyz/ws"
    async with websockets.connect(uri) as websocket:
        # 启动心跳任务
        heartbeat_task = asyncio.create_task(heartbeat(websocket))
        
        # 主循环：接收消息
        async for message in websocket:
            data = json.loads(message)
            if data.get("type") == "pong":
                print("收到心跳 pong")
            else:
                print(f"收到数据: {data}")

asyncio.run(main())

我曾经踩过的坑：心跳和主接收循环是并发的，但要注意异常处理。如果连接断了，心跳任务还在发消息，会抛出异常。所以我在心跳函数里加了 try-except，一旦连接关闭，就优雅退出。

12.3 订阅与取消订阅：按需获取数据

连接建立好了，心跳也稳了，接下来就是真正干活了——订阅数据。

Hyperliquid 的 WebSocket 支持多种订阅类型：

  • orderbook：订单簿数据（深度）
  • trade：成交数据
  • candle：K线数据
  • user：用户账户更新（需要认证）

订阅的格式也很清晰，就是一个 JSON 消息：

{
  "type": "subscribe",
  "channel": "orderbook",
  "coin": "BTC"
}

取消订阅类似，把 subscribe 换成 unsubscribe：

{
  "type": "unsubscribe",
  "channel": "orderbook",
  "coin": "BTC"
}

下面是一个完整的订阅示例，订阅 BTC 的订单簿和成交数据：

async def subscribe_channels(websocket):
    # 订阅订单簿
    sub_orderbook = {
        "type": "subscribe",
        "channel": "orderbook",
        "coin": "BTC"
    }
    await websocket.send(json.dumps(sub_orderbook))
    print("已订阅 BTC 订单簿")
    
    # 订阅成交
    sub_trade = {
        "type": "subscribe",
        "channel": "trade",
        "coin": "BTC"
    }
    await websocket.send(json.dumps(sub_trade))
    print("已订阅 BTC 成交")

async def unsubscribe_channel(websocket, channel, coin):
    unsub_msg = {
        "type": "unsubscribe",
        "channel": channel,
        "coin": coin
    }
    await websocket.send(json.dumps(unsub_msg))
    print(f"已取消订阅 {coin} 的 {channel}")

重要提示：订阅后，服务器会立即开始推送数据。如果你不需要某个频道了，记得取消订阅，否则会浪费带宽和资源。我在项目中见过有人订阅了十几个币的订单簿，结果只交易其中两个，白白浪费了流量。

最后，分享几个我实际项目中遇到的坑：

问题 表现 解决方案
连接被防火墙断开 长时间无数据后，连接静默断开 实现心跳机制，每30秒发送 ping
订阅过多频道 带宽占用高，消息处理不过来 只订阅需要的币种和频道，及时取消订阅
重连后状态丢失 重连后没有重新订阅，收不到数据 重连后，重新发送所有订阅请求
消息处理阻塞 心跳超时，被服务器断开 使用异步处理，不要阻塞事件循环

我的建议：刚开始做 WebSocket 对接时，先只订阅一个币种的一个频道（比如 BTC 的 orderbook），把整个流程跑通。确认心跳、重连、取消订阅都正常后，再逐步增加订阅内容。这样出了问题，排查范围小很多。

好了，WebSocket 的基础就这些。说白了就是三步：连上、保持、订阅。但每一步都有细节，尤其是心跳和重连，直接决定了你的策略能不能稳定运行。我见过太多人因为忽略了心跳，导致策略在关键时刻掉线，损失惨重。

嗯，希望这些经验能帮你少走弯路。
