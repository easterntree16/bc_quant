策略框架搭建（二）：信号生成模块、风险管理模块、订单执行模块

上一章我们把策略框架的骨架搭好了。今天咱们来填肉——把三个核心模块讲透：信号生成、风险管理、订单执行。这三个模块，说白了就是策略的「大脑」、「心脏」和「手脚」。

我个人习惯，写策略前会先画一张模块关系图。这样代码写起来才不会乱。来，先看看我画的这张图：

你看，数据从市场进来，经过信号生成模块判断方向，然后交给风险管理模块算仓位和止损，最后订单执行模块负责把单子发出去。每个环节都环环相扣。我在项目中遇到过不少新手，信号写得很漂亮，但风控一塌糊涂，结果爆仓了——嗯，这种教训太深刻了。

一、信号生成模块：策略的「大脑」

信号生成模块，说白了就是回答一个问题：现在该做多、做空，还是观望？

我个人习惯把信号生成拆成三层：

  1. 数据预处理层：清洗、对齐、计算衍生指标
  2. 信号计算层：跑技术指标、模式识别、多因子打分
  3. 信号聚合层：把多个子信号合并成一个最终决策

来看一个具体的代码实现。这是我在 Hyperliquid 上跑过的一个均值回归策略的信号生成器：

class SignalGenerator:
    """
    信号生成器 - 均值回归策略示例
    """
    def __init__(self, lookback: int = 20, z_threshold: float = 2.0):
        self.lookback = lookback
        self.z_threshold = z_threshold
        self.price_buffer = []  # 价格缓存

    def update_price(self, price: float):
        """更新价格数据"""
        self.price_buffer.append(price)
        if len(self.price_buffer) > self.lookback * 2:
            self.price_buffer.pop(0)

    def compute_zscore(self) -> float:
        """计算当前价格的Z-Score"""
        if len(self.price_buffer) < self.lookback:
            return 0.0

        recent = self.price_buffer[-self.lookback:]
        mean = sum(recent) / len(recent)
        variance = sum((x - mean) ** 2 for x in recent) / len(recent)
        std = variance ** 0.5

        if std == 0:
            return 0.0

        current_price = self.price_buffer[-1]
        zscore = (current_price - mean) / std
        return zscore

    def generate_signal(self) -> dict:
        """
        生成交易信号
        返回: {'action': 'buy'/'sell'/'hold', 'strength': 0.0~1.0, 'zscore': float}
        """
        zscore = self.compute_zscore()

        if zscore > self.z_threshold:
            # 价格偏高，做空信号
            strength = min((zscore - self.z_threshold) / self.z_threshold, 1.0)
            return {'action': 'sell', 'strength': strength, 'zscore': zscore}
        elif zscore < -self.z_threshold:
            # 价格偏低，做多信号
            strength = min((abs(zscore) - self.z_threshold) / self.z_threshold, 1.0)
            return {'action': 'buy', 'strength': strength, 'zscore': zscore}
        else:
            return {'action': 'hold', 'strength': 0.0, 'zscore': zscore}
💡 我的经验：信号强度（strength）这个字段很重要。它不只是告诉你方向，还告诉你「多确信」。我一般会把 strength 传给风控模块，让它根据置信度动态调整仓位。比如 strength=0.3 时只开 30% 仓位，strength=0.9 时满仓干。

你想想看，如果信号生成模块只输出「买」或「卖」，那风控模块就没办法做精细化的仓位管理了。所以，信号一定要带强度信息。

二、风险管理模块：策略的「心脏」

风险管理模块，我愿称之为策略的心脏。心脏停了，人就没了。风控没做好，账户就归零了。

我在 Hyperliquid 上见过太多人，策略信号很准，但因为没设止损，一次黑天鹅就爆仓了。嗯，我自己早期也吃过这个亏——有一次 ETH 插针，我的网格策略没设硬止损，直接穿了清算价，亏了 30%。从那以后，我把风控模块写成了策略里最「啰嗦」的部分。

一个完整的风险管理模块，至少包含以下功能：

功能 说明 实现要点
仓位计算 根据信号强度和账户余额计算开仓数量 考虑杠杆、保证金比例、最大仓位限制
止损管理 设置硬止损和移动止损 硬止损用固定价格，移动止损用 ATR 动态调整
止盈管理 分批止盈或追踪止盈 可以设多个目标价位，分批出场
最大回撤控制 当日/当周亏损超过阈值时暂停交易 记录每日盈亏，超过阈值自动熔断
相关性检查 避免多个相关品种同时开仓 维护一个持仓相关性矩阵

来看一个具体的仓位计算实现：

class RiskManager:
    """
    风险管理器 - 仓位计算 + 止损止盈
    """
    def __init__(self, account_balance: float, max_risk_per_trade: float = 0.02):
        self.account_balance = account_balance
        self.max_risk_per_trade = max_risk_per_trade  # 单笔最大风险比例 2%
        self.max_position_ratio = 0.5  # 最大仓位比例 50%
        self.daily_loss_limit = 0.08   # 日亏损上限 8%

    def calculate_position_size(self, signal_strength: float, entry_price: float,
                                stop_loss_price: float, leverage: int = 1) -> dict:
        """
        计算开仓数量
        :param signal_strength: 信号强度 0.0~1.0
        :param entry_price: 入场价格
        :param stop_loss_price: 止损价格
        :param leverage: 杠杆倍数
        :return: 仓位信息
        """
        # 1. 根据信号强度调整风险比例
        risk_per_trade = self.max_risk_per_trade * signal_strength

        # 2. 计算每单位价格波动带来的亏损
        price_risk = abs(entry_price - stop_loss_price)
        if price_risk == 0:
            return {'size': 0, 'reason': 'stop_loss_too_tight'}

        # 3. 计算可开仓数量（考虑杠杆）
        risk_amount = self.account_balance * risk_per_trade
        raw_size = risk_amount / price_risk

        # 4. 应用杠杆
        leveraged_size = raw_size * leverage

        # 5. 检查最大仓位限制
        max_size = (self.account_balance * self.max_position_ratio) / entry_price
        final_size = min(leveraged_size, max_size)

        return {
            'size': round(final_size, 4),
            'risk_amount': round(risk_amount, 2),
            'leverage': leverage,
            'stop_loss': stop_loss_price
        }

    def check_daily_loss_limit(self, daily_pnl: float) -> bool:
        """检查是否触发日亏损上限"""
        loss_ratio = abs(daily_pnl) / self.account_balance
        if loss_ratio >= self.daily_loss_limit:
            return True  # 触发熔断
        return False
⚠️ 避坑指南：我曾经犯过一个错误——把止损价格设得太近，结果被市场噪音反复扫损。后来我改用 ATR（平均真实波幅）来动态计算止损距离，效果好了很多。建议止损距离至少是 1.5 倍 ATR。

这里有个细节要注意：风控模块一定要独立于信号模块运行。什么意思？就是即使信号模块挂了，风控模块还能独立执行止损和熔断。我在 Hyperliquid 上就是这么设计的——风控逻辑跑在一个单独的协程里，每 100ms 检查一次持仓状态。

三、订单执行模块：策略的「手脚」

信号算好了，仓位算好了，接下来就是执行。订单执行模块，说白了就是把「想买」变成「买到了」。

Hyperliquid 的订单执行有几个关键点：

  • 订单类型：限价单 vs 市价单。我个人习惯用限价单，除非信号特别强才用市价单
  • 滑点控制：限价单要设置合理的价格偏移，避免一直吃不到单
  • 订单生命周期管理：下单 -> 监控 -> 成交/取消 -> 重试
  • 错误处理：网络超时、余额不足、价格保护等异常情况

来看一个订单执行器的核心实现：

class OrderExecutor:
    """
    订单执行器 - 对接 Hyperliquid API
    """
    def __init__(self, hyperliquid_client, max_retries: int = 3):
        self.client = hyperliquid_client
        self.max_retries = max_retries
        self.pending_orders = {}  # 维护未成交订单

    async def execute_market_order(self, symbol: str, side: str, size: float,
                                   slippage_bps: int = 5) -> dict:
        """
        执行市价单（带滑点保护）
        :param slippage_bps: 允许的滑点，单位基点（1bps = 0.01%）
        """
        # 获取当前最优价格
        orderbook = await self.client.get_orderbook(symbol)
        if side == 'buy':
            price = orderbook['asks'][0]['price'] * (1 + slippage_bps / 10000)
        else:
            price = orderbook['bids'][0]['price'] * (1 - slippage_bps / 10000)

        # 构建订单
        order = {
            'symbol': symbol,
            'side': side,
            'size': size,
            'order_type': 'market',
            'price': price,
            'reduce_only': False
        }

        # 发送订单（带重试）
        for attempt in range(self.max_retries):
            try:
                response = await self.client.place_order(order)
                if response['status'] == 'filled':
                    return {'status': 'filled', 'order_id': response['oid'],
                            'fill_price': response['avg_price']}
                elif response['status'] == 'pending':
                    # 市价单一般不会pending，但以防万一
                    self.pending_orders[response['oid']] = order
                    return {'status': 'pending', 'order_id': response['oid']}
            except Exception as e:
                if attempt == self.max_retries - 1:
                    return {'status': 'failed', 'error': str(e)}
                await asyncio.sleep(0.1 * (attempt + 1))  # 退避重试

        return {'status': 'failed', 'error': 'max_retries_exceeded'}

    async def cancel_all_orders(self, symbol: str = None):
        """取消所有未成交订单"""
        if symbol:
            orders = await self.client.get_open_orders(symbol)
        else:
            orders = await self.client.get_open_orders()

        for order in orders:
            await self.client.cancel_order(order['oid'])
            self.pending_orders.pop(order['oid'], None)
💡 我的经验：订单执行模块一定要做「幂等性处理」。什么意思？就是同一个订单不要因为网络重试而重复发送。我一般会在发送前生成一个唯一的 client_order_id，Hyperliquid 支持这个字段，重复的 ID 会被自动拒绝。

你想想看，如果网络抖动了一下，你的订单其实已经成交了，但客户端没收到确认，又发了一次——那就变成双倍仓位了。这种 bug 在实盘中是要命的。

三个模块如何协作？

最后，我简单说一下这三个模块怎么串起来。在我的策略框架里，主循环大概是这样的：

async def strategy_loop():
    """策略主循环"""
    signal_gen = SignalGenerator(lookback=20, z_threshold=2.0)
    risk_mgr = RiskManager(account_balance=10000.0, max_risk_per_trade=0.02)
    executor = OrderExecutor(hyperliquid_client=client)

    while True:
        # 1. 获取最新价格
        price = await get_latest_price('ETH')
        signal_gen.update_price(price)

        # 2. 生成信号
        signal = signal_gen.generate_signal()
        if signal['action'] == 'hold':
            await asyncio.sleep(1)
            continue

        # 3. 计算仓位和止损
        stop_loss = price * 0.98 if signal['action'] == 'buy' else price * 1.02
        position = risk_mgr.calculate_position_size(
            signal_strength=signal['strength'],
            entry_price=price,
            stop_loss_price=stop_loss,
            leverage=2
        )

        if position['size'] == 0:
            await asyncio.sleep(1)
            continue

        # 4. 执行订单
        result = await executor.execute_market_order(
            symbol='ETH',
            side=signal['action'],
            size=position['size'],
            slippage_bps=5
        )

        # 5. 记录日志
        logger.info(f"Signal: {signal['action']}, Size: {position['size']}, "
                    f"Result: {result['status']}")

        await asyncio.sleep(1)

嗯，这个循环看起来简单，但每个环节都有很多细节。我在 Hyperliquid 上跑策略时，还会加一个「预热阶段」——先跑 100 个 tick 的数据，让信号生成器的缓存填满，再开始真正交易。这个小技巧帮我避免了不少开局就乱开仓的情况。

好了，三个模块的核心逻辑就讲到这里。记住一句话：信号是方向，风控是底线，执行是保障。三者缺一不可。

📌 本章核心要点：

  • 信号生成模块要输出「方向 + 强度」，不要只输出方向
  • 风险管理模块要独立运行，不能依赖信号模块
  • 订单执行模块必须做幂等性处理和重试机制
  • 三个模块通过主循环串联，数据流是单向的：信号 -> 风控 -> 执行
