WebSocket 实战（一）：实时订单簿数据流、增量更新与全量快照

做量化交易，最核心的就是数据。尤其是订单簿数据，它直接反映了市场的深度和流动性。我个人习惯把订单簿比作市场的「心电图」——跳得快不快、跳得稳不稳，全看它。

今天我们就来聊聊，怎么用 WebSocket 从 Hyperliquid 拿到这份「心电图」，并且保证数据不丢、不乱、不延迟。

为什么需要 WebSocket？

你想想看，如果用 REST API 去轮询订单簿，每秒钟拉一次，延迟至少几百毫秒。这在高频场景下根本没法用。WebSocket 就不一样了，它是一条长连接，服务器主动往你这边推数据。说白了，就是「你躺着，数据自己送上门」。

我在项目中遇到过最夸张的情况：用 REST 轮询时，订单簿中间层数据已经变了三次，我这边才拿到第一次的快照。那笔交易亏得我印象深刻。嗯，从那以后，所有实时数据我都改用 WebSocket 了。

Hyperliquid 的 WebSocket 架构

Hyperliquid 的 WebSocket 接口设计得挺清爽。它主要提供两种数据流：

  • 全量快照（snapshot）：当前订单簿的完整状态，包含所有档位的买盘和卖盘
  • 增量更新（delta）：每次变化只推送变化的部分，比如某档位价格变了、某档位被吃掉了

这两种数据必须配合使用。你不能只靠增量更新，因为万一中间断连了，你的本地数据就跟服务器对不上了。正确的做法是：先拿一次全量快照作为基准，然后不断叠加增量更新。

核心原则：全量快照是地基，增量更新是砖瓦。地基不稳，房子迟早塌。

实战：连接并订阅订单簿

好，理论说完了，咱们直接上代码。我个人习惯用 websockets 这个库，它比 socket.io 轻量，而且原生支持 asyncio。

import json
import websockets

async def subscribe_orderbook():

处理全量快照

第一次连接成功后，服务器会先推送一个全量快照。它的结构大概是这样的：

{
    "type": "snapshot",
    "data": {
        "bids": [
            ["10000.5", "1.2"],
            ["9999.8", "0.5"]
        ],
        "asks": [
            ["10001.0", "0.8"],
            ["10001.5", "1.0"]
        ]
    }
}

注意，价格和数量都是字符串。为什么不用浮点数？因为浮点数有精度问题。你想想看，0.1 + 0.2 在 Python 里等于多少？0.30000000000000004。这在交易系统里是不能接受的。所以 Hyperliquid 很聪明地用了字符串。

收到快照后，我建议直接替换掉本地存储的订单簿，而不是合并。因为快照代表的是当前时刻的完整状态，任何本地残留数据都是过时的。

class OrderBook:
    def __init__(self):
        self.bids = {}  # 价格 -> 数量
        self.asks = {}
    
    def apply_snapshot(self, snapshot):
        """全量快照：直接替换"""
        self.bids = {float(price): float(qty) 
                     for price, qty in snapshot['bids']}
        self.asks = {float(price): float(qty) 
                     for price, qty in snapshot['asks']}
        print(f"快照已应用：{len(self.bids)} 档买盘，{len(self.asks)} 档卖盘")

处理增量更新

快照之后，服务器就开始推送增量更新了。增量更新的格式是这样的：

{
    "type": "delta",
    "data": {
        "bids": [["10000.5", "0"]],   # 数量为0表示删除该档位
        "asks": [["10002.0", "1.5"]]  # 新增或更新档位
    }
}

这里有个关键点：数量为 0 表示该价格档位被完全吃掉了，需要从本地订单簿中删除。数量大于 0 则更新或新增。

避坑指南：我曾经遇到过一个问题——增量更新里的价格在本地订单簿中找不到。这种情况通常是因为网络延迟导致快照还没到，增量先到了。解决方案是：如果增量中的价格不在本地，直接忽略它，等下一次快照来修正。

def apply_delta(self, delta):
    """增量更新：合并到现有订单簿"""
    for price_str, qty_str in delta['bids']:
        price = float(price_str)
        qty = float(qty_str)
        
        if qty == 0:
            # 删除该档位
            self.bids.pop(price, None)
        else:
            # 更新或新增
            self.bids[price] = qty
    
    # 卖盘同理
    for price_str, qty_str in delta['asks']:
        price = float(price_str)
        qty = float(qty_str)
        
        if qty == 0:
            self.asks.pop(price, None)
        else:
            self.asks[price] = qty

保持数据一致性

在实际运行中，WebSocket 连接可能会断开。断开后重连时，必须重新获取全量快照。你不能假设增量更新是连续的。

我建议的流程是：

  1. 建立 WebSocket 连接
  2. 订阅订单簿频道
  3. 等待全量快照，替换本地数据
  4. 持续接收增量更新，合并到本地
  5. 如果连接断开，回到第 1 步

这个流程看起来简单，但实际做起来有个坑：快照和增量之间可能有时间差。也就是说，你收到快照的那一瞬间，市场可能已经变了。等你开始处理增量时，中间有几笔更新已经丢了。

怎么解决？Hyperliquid 的增量更新里带了一个序列号（seqNum），你可以用它来检查是否有遗漏。如果发现序列号不连续，说明中间有数据丢了，这时候需要重新请求一次全量快照。

def check_sequence(self, new_seq):
    """检查序列号是否连续"""
    if self.last_seq is not None and new_seq != self.last_seq + 1:
        print(f"警告：序列号不连续！期望 {self.last_seq + 1}，实际 {new_seq}")
        # 触发重新获取快照
        return False
    self.last_seq = new_seq
    return True

重要提醒：序列号检查不是可选项，是必选项。我在生产环境中遇到过两次序列号跳变，都是因为服务器端短暂重启导致的。如果不检查，你的订单簿会慢慢「漂移」，最终跟真实市场差出好几个档位。

性能优化建议

订单簿数据量很大，尤其是深度比较深的币种。我见过 BTC 的订单簿有上百档数据，每秒更新几十次。如果处理不当，CPU 很快就跑满了。

几个优化点：

  • 使用字典而不是列表：价格作为 key，查找速度是 O(1)
  • 避免频繁排序：只在需要计算买卖价差或深度时排序
  • 批量处理增量：如果短时间内收到多个增量，可以合并后再更新
  • 使用 decimal 模块：如果对精度要求极高，别用 float

嗯，说到 decimal，我踩过一个坑。有一次我用 float 做价格比较，结果两个看起来一样的价格，因为浮点误差被判为不相等，导致订单簿里出现了重复档位。排查了半天才发现是精度问题。从那以后，涉及价格比较的地方我都用 decimal 了。

完整代码示例

最后，我把上面所有的逻辑整合成一个完整的类。你可以直接拿去用：

import asyncio
import json
import websockets
from decimal import Decimal

class HyperliquidOrderBook:
    def __init__(self, coin="BTC"):
        self.coin = coin
        self.bids = {}
        self.asks = {}
        self.last_seq = None
        self.ws = None
    
    async def connect(self):
        uri = "wss://api.hyperliquid.xyz/ws"
        self.ws = await websockets.connect(uri)
        
        # 订阅
        msg = {"type": "subscribe", "channel": "orderbook", "coin": self.coin}
        await self.ws.send(json.dumps(msg))
        
        async for message in self.ws:
            data = json.loads(message)
            if data['type'] == 'snapshot':
                self._apply_snapshot(data['data'])
            elif data['type'] == 'delta':
                self._apply_delta(data['data'])
    
    def _apply_snapshot(self, data):
        self.bids = {Decimal(price): Decimal(qty) 
                     for price, qty in data['bids']}
        self.asks = {Decimal(price): Decimal(qty) 
                     for price, qty in data['asks']}
        self.last_seq = data.get('seqNum')
    
    def _apply_delta(self, data):
        # 检查序列号
        seq = data.get('seqNum')
        if seq and self.last_seq and seq != self.last_seq + 1:
            print("序列号不连续，需要重新获取快照")
            return
        
        self.last_seq = seq
        
        # 处理买盘增量
        for price_str, qty_str in data['bids']:
            price = Decimal(price_str)
            qty = Decimal(qty_str)
            if qty == 0:
                self.bids.pop(price, None)
            else:
                self.bids[price] = qty
        
        # 处理卖盘增量
        for price_str, qty_str in data['asks']:
            price = Decimal(price_str)
            qty = Decimal(qty_str)
            if qty == 0:
                self.asks.pop(price, None)
            else:
                self.asks[price] = qty
    
    def get_best_bid(self):
        return max(self.bids.keys()) if self.bids else None
    
    def get_best_ask(self):
        return min(self.asks.keys()) if self.asks else None
    
    def get_spread(self):
        bid = self.get_best_bid()
        ask = self.get_best_ask()
        if bid and ask:
            return float(ask - bid)
        return None

这个类封装了连接、订阅、快照处理、增量更新和序列号检查。你只需要实例化它，然后调用 connect() 方法，就能拿到实时订单簿了。

实际跑起来之后，你可以用 get_best_bid() 和 get_best_ask() 获取当前最优买卖价，计算价差，或者进一步做策略判断。

好了，WebSocket 订单簿的基础就讲到这里。记住三个关键词：全量快照做基准、增量更新持续叠加、序列号检查保一致。把这三点做好，你的订单簿数据就不会出大问题。
